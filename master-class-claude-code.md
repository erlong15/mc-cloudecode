# Мастер-класс: Claude Code — построение проекта агентной системой

**Формат:** онлайн-воркшоп, ориентировочно 145 минут. Ведущий показывает — участники повторяют на своих машинах; после ключевых блоков проверка «получилось ли» и открытое обсуждение. Воркшоп для своих: тайминг — ориентир, приоритет отдаётся практике; выход за 2 часа допустим.

**Аудитория:** DevOps-инженеры, DBA, разработчики, техлиды. Участники уже пробовали Claude Code для отдельных задач, но не выстраивали систему его расширений.

**Основная идея.** Claude Code — это агент, а не диалоговый помощник. Возможности Claude Code складываются в систему расширений, которую выстраивают вокруг двух понятий: **контекст** — то, что агент знает о проекте, и **границы** — то, какие действия ему разрешены. Занятие показывает эту систему в работе: настроенная агентная система строит проект с нуля.

---

## Сквозной сценарий воркшопа

Воркшоп построен как единый сквозной сценарий: **из пустого репозитория агентная система создаёт работающий бэкенд-проект**, а участники по ходу настраивают её узлы.

**Исходное состояние.** Пустой Git-репозиторий на GitHub. Ни строчки кода, ни конфигурации.

**Цель применения агентов.** Собрать конфигурацию (память проекта, правила, навыки, субагенты, границы, автоматические проверки), поставить агенту цель — и получить проект, доведённый до состояния, пригодного для публикации: с кодом, тестами, локальным стендом, чартом для Kubernetes, конвейером CI, документацией и архитектурными решениями.

**Предметная область.** Книжный магазин **OhMyClaude Books** на Laravel, работающий **без php-fpm**: современные рантаймы с постоянными воркерами вместо модели FastCGI-процессов. Это даёт занятию техническую остроту, интересную DevOps-аудитории, и превращает архитектурное решение о выборе рантайма в содержательный ADR, а не в формальность.

Книжный каталог удобен как предметная область: у него нетривиальная модель данных (книга — автор — серия — жанры — теги, связи «многие ко многим»), естественная потребность в полнотекстовом поиске и фильтрации, и достаточный объём записей, чтобы демонстрация выглядела живой, а не набором «Товар 1, Товар 2».

**Состав целевого продукта:**

| Слой | Артефакт |
|------|----------|
| Сервисы | два Laravel-сервиса: каталог книг и заказы, на разных современных рантаймах |
| Данные | PostgreSQL, миграции, скрипты наполнения каталога; Redis для кэша и очередей |
| Локальный стенд | `docker-compose.yml` с healthcheck'ами: `up` — и магазин работает |
| Контейнеризация | Dockerfile на сервис: multi-stage, non-root, зафиксированные версии |
| Kubernetes | Helm-чарт: deployment, service, configmap, secret, values, ingress |
| Качество | unit-тесты и интеграционные проверки через стенд |
| CI | GitHub Actions на бесплатных runner'ах: линт, тесты, сборка, проверка безопасности, ревью изменений агентом |
| Документация | README, ADR в `docs/adr/`, архитектурная схема на Mermaid (рендерится GitHub нативно) |
| История | осмысленные коммиты и pull request с ревью |

**Термины стека — пояснять по ходу.** Аудитория смешанная, и Laravel-специфичная лексика знакома не всем. Короткие определения, которых достаточно для понимания занятия:

| Термин | Пояснение в одну строку |
|--------|--------------------------|
| **Миграция** | версионированное изменение **структуры** БД: таблицы, колонки, индексы (аналог DDL) |
| **Скрипт наполнения** | класс, наполняющий базу **данными** (аналог INSERT). В Laravel называется seeder, лежит в `database/seeders/`, запуск — `php artisan db:seed` |
| **artisan** | консольная утилита Laravel: миграции, тесты, запуск приложения, свои команды |
| **Eloquent** | ORM Laravel: работа с таблицами через объекты-модели |
| **Pest** | фреймворк тестов, применяемый в Laravel по умолчанию; запуск — `php artisan test` |
| **Octane** | режим, в котором приложение загружается один раз и **живёт между запросами**, вместо запуска процесса на каждый запрос |
| **worker-режим** | следствие Octane: постоянный процесс-воркер обслуживает запросы подряд — отсюда требования к состоянию в коде |
| **php-fpm / FastCGI** | классическая схема: на каждый запрос поднимается процесс PHP; от неё мы и уходим |

Наиболее важна для занятия последняя пара: именно отказ от php-fpm делает архитектурное решение содержательным и порождает ограничения, вынесенные в правило `octane.md`.

**Наполнение каталога: парсер плюс базовый скрипт наполнения.** Этап решает практическую задачу и одновременно даёт две методические демонстрации.

Схема из двух слоёв:

1. **Парсер каталога** — консольный инструмент проекта, который собирает публичные метаданные стороннего каталога (источник структуры — площадка самиздата) и складывает выгрузку в `storage/catalog/`, исключённый из репозитория. Дисциплина запросов вынесена в правило `scraping.md`: проверка `robots.txt`, ограничение частоты, backoff, описательный `User-Agent`, кэширование ответов, запросы через HTTP-клиент приложения. Собираются структурные метаданные; обложки и полные аннотации не сохраняются.
2. **Базовый скрипт наполнения на синтетических данных**, который коммитится в репозиторий и работает без парсера. Проект должен запускаться у любого, кто его склонировал, без доступа к внешнему источнику. Если выгрузка парсера присутствует, скрипт использует её.

**Первая демонстрация — работа с незнакомой внешней структурой.** Агент сам разбирается, как устроены страница списка и карточка, что разрешает `robots.txt`, как устроена пагинация. Это узнаваемая рабочая задача, а не учебное упражнение.

**Вторая демонстрация — граница, которую мы сознательно не ставили.** На разведке агент выходит в сеть встроенным инструментом `WebFetch`, а не shell-командой, поэтому запрет `Bash(curl:*)` из блока 3 его не касается — и это правильное поведение, а не пробел. Разобрать вслух (подробности в заметках спикера): запрет `curl` защищает от выполнения чужого кода (`curl … | bash`), а не от чтения страницы; чтение сети — это и есть работа, ради которой мы пишем парсер. Закрыв `WebFetch`, мы сломали бы задачу и получили бы ограничение, которое в реальном проекте отключат целиком.

**Реальный риск чтения — инъекция через содержимое.** Текст страницы попадает в контекст и читается моделью наравне с инструкциями человека; враждебная страница может содержать указания, адресованные агенту. Запрет инструмента решает это грубо; меры по убыванию силы:

1. **Не помещать сырой текст в контекст — читать кодом, а не агентом.** Это и есть архитектура нашего парсера, и стоит проговорить её именно как меру безопасности, а не только как инженерную опрятность: после написания парсера загрузку выполняет приложение, результат пишется в файл, агент работает со структурированными данными. Сырой HTML в контекст не попадает. Агентом читается только разведка — короткий шаг под присмотром.
2. **Изолировать чтение в субагенте** с инструментами только на чтение: в основную сессию возвращается сводка, а не исходный текст; у исполнителя нет прав на запись и выполнение команд, поэтому ущерб от инъекции ограничен по построению. Здесь субагенты из блока 6 работают как средство безопасности, а не только экономии контекста.
3. **Ограничение по доменам** (`WebFetch(domain:…)`) — сужает поверхность, но не защищает от инъекции с самого разрешённого домена.
4. **Просьба считать прочитанное данными, а не инструкциями** — слабейшая мера: это обращение к модели, а не правило harness.

Полезная деталь об инструменте: `WebFetch` не переносит страницу дословно — он отвечает на заданный вопрос по её содержимому, что уменьшает объём чужого текста в контексте, но не устраняет риск, поскольку ответ построен на недоверенном источнике.

**Вывод, замыкающий блок 3:** у каждого правила должна быть названа своя угроза — и выбрана мера, которая эту угрозу действительно закрывает. Против инъекции работает не запрет сети, а то, где именно оказывается прочитанный текст.

**Ключевой приём проведения.** Постройка запускается примерно в середине занятия и **работает в фоне**, пока разбираются субагенты, автономные режимы и стоимость. Ведущий периодически переключается на прогресс. К финалу проект готов, и последние блоки — ревью, документирование, ADR — выполняются уже поверх созданного кода.

> Перед проведением необходимо свериться с актуальной документацией: версии моделей, цены, формат hooks, версии Laravel и рантаймов меняются. Ссылки — в конце документа.

## Что слушатель получит с мастер-класса

1. **Понимание устройства агента** (модель + harness) и **карту возможностей** с принципом «какую возможность применять в какой ситуации».
2. **Отработанный руками навык:** создать память проекта, написать правило и навык, поднять субагента, закрыть агенту опасные действия через `permissions` и hooks.
3. **Метод постановки задачи агенту**, при котором тот способен построить проект целиком: план до кода, проверяемые критерии готовности, автономное доведение до результата.
4. **Готовый репозиторий-шаблон конфигурации** (`CLAUDE.md`, `.claude/`) и **письменный туториал** (`TUTORIAL.md`) — переносится в свой проект в тот же день.
5. **Рецепт встраивания в pipeline:** headless-режим и job ревью на GitHub Actions.
6. **Понимание модели стоимости** — с реальной цифрой расхода на постройку проекта, измеренной на занятии.
7. **Наблюдаемый масштабный результат:** работающий проект, созданный агентной системой за время занятия.

**По ролям:**

| Роль | Что забирает |
|------|--------------|
| Разработчик | метод постановки задач, навык-чеклист ревью, субагент-ревьюер, доведение до зелёных тестов |
| DBA | правила для миграций и SQL, субагент ревью схемы, контроль изменений БД до попадания в прод |
| DevOps | границы и hooks как guardrails as code, headless-режим в GitHub Actions, периодические проверки |
| Техлид | иерархия настроек, тиражирование конфигурации на команду, контроль стоимости, чек-лист внедрения |

**Что нужно участнику заранее:** установленный Claude Code, подписка Pro/Max/Team Premium или ключ API, аккаунт GitHub, установленный Docker, терминал.

## Блок 0. Цель занятия: что построим (6 минут)

**Цель:** с первой минуты показать масштаб результата, чтобы дальнейшая настройка воспринималась как средство, а не как самоцель.

**Показ:** открыть эталонный репозиторий с результатом полного прогона (готовится на репетиции) и пройти по нему за две минуты: два сервиса, стенд поднимается одной командой, чарт, CI, ADR, схема. Затем закрыть и вернуться к пустому репозиторию: «всё это будет создано на ваших глазах».

**Тезис для слайда:**

> Сегодня мы не пишем код. Мы **настраиваем систему**, которая напишет его сама, — и учимся эту систему ограничивать и проверять.

**Проговорить состав продукта** по таблице целевых артефактов и предметную область: книжный магазин на Laravel без php-fpm, на рантаймах с постоянными воркерами. Отметить, что выбор рантайма станет предметом ADR в блоке 10.

## Блок 1. Агент = модель + harness (12 минут)

**Цель:** заложить понятие, на котором держится весь материал.

**Слайд 1 — что умеет модель.** Модель умеет одно: читать текст и порождать текст, включая запрос «вызови такой-то инструмент». Она не запускает команды, не читает файлы и не помнит ничего между запросами — она stateless.

**Слайд 2 — что делает harness.** Claude Code — это harness: обвязка, которая собирает каждый запрос, ведёт цикл, исполняет инструменты, проверяет права и управляет контекстом. **Агент = модель + harness.**

**Слайд 3 — что уходит в каждый запрос** (окно контекста ≈ 200 000 токенов): системный промпт → CLAUDE.md и правила, подгруженные под текущие файлы → описания инструментов, навыков, имена MCP-инструментов → история диалога с результатами вызовов. Всё это конкурирует за одно окно — отсюда сквозная тема экономии контекста.

**Слайд 4 — агентный цикл:**

```
задача → модель выбирает инструмент
       → harness: PreToolUse hook → permissions (deny/ask/allow) → выполнение → PostToolUse hook
       → результат в контекст → снова модель → … → результат
```

Отметить точки расширения: память и правила входят в запрос; навыки и MCP расширяют набор инструментов; permissions и hooks стоят на пути каждого вызова; субагент — отдельный такой же цикл со своим окном.

**Показ:** в пустом репозитории дать агенту первую задачу и комментировать цикл вслух.

**Вывод блока:**

> Просьбы живут в модели — она старается, но может забыть. Правила живут в harness — они срабатывают всегда. Отсюда два понятия занятия: **контекст** и **границы**.

## Блок 2. Пустой репозиторий → память и навыки проекта (22 минуты)

**Цель:** создать конфигурацию, которая объяснит агенту, что и по каким соглашениям строить. Первая практика участников.

**Ключевые положения:**

- **CLAUDE.md** загружается в каждый запрос: карта проекта, соглашения, ограничения. Рекомендуемый объём — до 200 строк; всё остальное выносится в правила и навыки. Создаётся командой `/init`, но в пустом репозитории пишется под задачу.
- **`.claude/rules/`** — тематические правила. Файл без `paths` действует всегда; файл с `paths` (glob-паттерны) подгружается только при работе с совпавшими файлами. Для нашего проекта: правила PHP/Laravel, правила рантайма и worker-режима, правила контейнеров, правила Helm-чарта, правила миграций.
- **`.claude/skills/`** — процедуры и чеклисты по запросу; в контексте на старте только описания.
- **Зрелый пример экосистемы навыков** (назвать аудитории): репозиторий mattpocock/skills — около 25 навыков, разделённых на **пользовательские** (вызываются человеком: `/grill-me` — интервью по плану, `/to-spec` — синтез разговора в спецификацию, `/handoff` — документ передачи работы) и **модельные** (агент применяет сам: `/tdd`, `/diagnosing-bugs`, `/code-review`). Это то же разделение, что наш параметр `disable-model-invocation`, доведённое до системы. Философия автора совпадает с нашей: навыки маленькие, редактируемые и композируемые — в противовес фреймворкам, отнимающим контроль.
- **Приём оттуда же — общий язык проекта:** словарь доменных терминов (в CLAUDE.md или отдельном файле, подключённом через `@`), где повторяющимся понятиям даны короткие имена. Сокращает многословность агента, расход токенов и разночтения в коде.
- **`.claude/agents/`** — субагенты; создаются здесь же, применяются в блоке 6.
- Конфигурацию пишем **на английском**: её читает модель. Общаться с агентом в чате можно по-русски.

**Ключевой приём (проговорить):** конфигурацию агента создаёт сам агент — по одному промпту на артефакт. Это быстрее и даёт корректный формат; человек проверяет и правит.

**Показ:** промпты из плейбука `PROMPTS.md` — CLAUDE.md с описанием целевой архитектуры → набор правил → навык ревью изменений.

**Практика участников (7 минут):** в своём проекте выполнить `/init`, прочитать результат, добавить одно соглашение, которое агент не угадал. **Проверка:** задать агенту вопрос, ответ на который есть только в CLAUDE.md.

**Ключевой вывод:** правило в CLAUDE.md задаёт намерение. Гарантированное исполнение обеспечивают блоки 3 (границы) и hooks.

## Блок 3. Границы: settings.json и hooks (15 минут)

**Цель:** ограничить агента **до** того, как он начнёт строить. Вторая практика.

**Иерархия настроек** (по убыванию приоритета): `managed-settings.json` (политика организации) → `--settings` (CLI, для сценариев и CI) → `.claude/settings.local.json` (личные) → `.claude/settings.json` (проектные, в репозитории) → `~/.claude/settings.json` (личные для всех проектов). Значения приоритетного уровня заменяют менее приоритетные, массивы и правила доступа объединяются.

**Управление доступом:**

- `permissions` содержит `allow`, `ask`, `deny`, а также `defaultMode` и `additionalDirectories`.
- Порядок проверки: `deny` → `ask` → `allow`, применяется первое совпавшее правило.
- Синтаксис: `Bash(php artisan:*)`, `Read(**/.env)`, MCP-инструменты — `mcp__github__create_pull_request`.
- Важный нюанс: сопоставление префиксное, поэтому `Bash(git push:*)` не поймает составную команду вида `cd x && git push`. Составные команды перехватывает hook.

**Hooks — события:**

| Событие | Когда срабатывает | Применение в нашем проекте |
|---------|-------------------|----------------------------|
| `PreToolUse` | перед вызовом инструмента | блокировка опасных команд и составных конструкций |
| `PostToolUse` | после успешного вызова | автоформат кода, поиск секретов после записи файлов |
| `UserPromptSubmit` | при отправке промпта | добавление контекста в запрос |
| `SessionStart` | старт или возобновление сессии | подгрузка состояния стенда |
| `Stop` | агент завершает ход | проверка полноты работы |

**Механика:** `matcher` — regex по имени инструмента; на stdin приходит JSON с `tool_name` и `tool_input`; **exit 0** — разрешено, **exit 2** — заблокировано, текст из stderr возвращается модели, и она перестраивается; тонкое управление — JSON-ответ с `permissionDecision`. Hook — код с правами пользователя: хранится в репозитории и ревьюится как код. Отладка: `claude --debug`.

**Показ:** запрет чтения `.env` и ключей, подтверждение на `git push`, разрешение на команды сборки и тестов; hook, блокирующий загрузку и выполнение скриптов из сети.

**Практика участников (5 минут):** добавить в свой проект `deny` на секреты и `ask` на push. **Проверка:** попросить агента прочитать `.env` и получить отказ.

**Ключевой принцип проектирования границ — у каждого правила названа своя угроза.** Правило, написанное «на всякий случай», невозможно оценить: непонятно, работает оно или нет. Разберём на живом примере из нашей же конфигурации:

| Правило | От какой угрозы | От чего **не** защищает |
|---------|-----------------|--------------------------|
| `deny Bash(curl:*)`, `Bash(wget:*)` | выполнение чужого кода в оболочке (`curl … \| bash`) | сетевого доступа как такового |
| `deny Read(**/.env)` | утечка секретов через контекст | записи секретов агентом в другой файл |
| `ask Bash(git push:*)` | необратимая публикация изменений | локальных изменений в рабочем дереве |

Отсюда практическое следствие, о котором прямо предупреждает документация: **сетевой доступ у агента имеет несколько путей** — встроенные инструменты `WebFetch` и `WebSearch` и shell-команды. Ограничение одного пути не закрывает возможность: запрет `Bash(curl:*)` не мешает агенту прочитать страницу через `WebFetch`, и наоборот — ограничение `WebFetch` бессмысленно, если разрешён произвольный `Bash`.

**Вывод для аудитории:** границы задаются по возможностям, а не по командам. И обратное, столь же важное: **не всякая незакрытая возможность — дыра.** Рефлекс «запретить всё, что не запрещено» порождает конфигурации настолько неудобные, что их отключают целиком — вместе с полезными правилами. Прежде чем закрывать — назвать угрозу и проверить, что она реальна для этого проекта.

**Синтаксис ограничения сетевых инструментов** (на случай, если угроза реальна): `WebFetch` целиком — `"deny": ["WebFetch"]`, инструмент исчезает из набора агента; по домену — `WebFetch(domain:example.com)`, поддерживается `*.example.com` (поддомены, но не сам домен). Для `WebSearch` ограничения по доменам нет — только инструмент целиком. Отдельный слой — песочница с собственным списком разрешённых доменов, действующая на sandbox-команды.

**Связка:** permissions (границы) и hooks (автоматика) вместе образуют guardrails as code — правила безопасности лежат в репозитории рядом с кодом.

## Блок 5. Постановка задачи, парсер каталога и запуск постройки (16 минут)

**Цель:** показать метод постановки задачи, при котором агент способен построить проект целиком, и запустить постройку в фоне.

**Метод — четыре элемента корректной постановки:**

1. **План до кода.** Работа начинается в режиме планирования (plan mode): агент изучает задачу и предлагает архитектурный план, ничего не записывая. План читает и утверждает человек — это точка контроля, дешёвая по сравнению с правкой готового кода. Вариант усиления — попросить агента сначала провести интервью по требованиям, добиваясь обоснования каждого решения; в сообществе этот приём оформлен как skill `grill-me` (репозиторий mattpocock/skills).

   **Механика режима — разобрать на слайде, это практический навык для всех.** `Shift+Tab` переключает режимы разрешений прямо в строке ввода, без перезапуска сессии: `default` → `acceptEdits` → `plan` → (дополнительные режимы, если доступны) → `default`; текущий режим виден в статусной строке. В `plan` разрешены чтение и поиск (`Read`, `Grep`, `Glob`), исследовательские команды оболочки из read-only набора и чтение документации; запись файлов, коммиты и изменяющие команды заблокированы. Выход из режима — не команда, а **выбор из трёх вариантов**, который агент предлагает вместе с готовым планом: принять и выполнять; принять, но подтверждать каждую правку; продолжить планирование с вашими замечаниями. План можно открыть в редакторе и поправить перед запуском. Войти можно и сразу: `claude --permission-mode plan` либо `defaultMode: "plan"` в настройках; выбранный режим запоминается при возобновлении сессии.

   **Не путать с субагентом `Plan`:** режим — состояние всей вашей сессии, в котором изменения заблокированы до утверждения плана; субагент — отдельный исполнитель с собственным чистым контекстом, возвращающий сводку. Первое применяют, когда крупную задачу ведёте вы сами; второе — когда нужно исследовать участок кода, не расходуя основной контекст.

   **Когда режим оправдан:** первое погружение в незнакомый код, чувствительные изменения (аутентификация, миграции), крупные рефакторинги, длинные сессии с обилием подтверждений. **Когда мешает:** однострочные починки, быстрая итеративная работа, генерация кода с нуля — исследовать нечего.
2. **Проверяемый критерий готовности.** Не «сделай магазин», а перечень условий: стенд поднимается одной командой, эндпоинты отвечают, тесты проходят, линтер чист, чарт валиден.
3. **Порядок работы.** Явно задать последовательность: каркас сервисов → БД и миграции → наполнение каталога → бизнес-логика → тесты → контейнеризация → стенд → чарт → CI → документация; коммит после каждого завершённого этапа.
4. **Автономное доведение.** `/goal` с критерием готовности: агент повторяет работу ход за ходом, пока условие не выполнено.

   **Механика, которую стоит разобрать явно.** Цель **сама является директивой**: команда немедленно начинает ход, отдельный промпт с задачей не нужен. После каждого хода условие независимо проверяет быстрая модель — «выполнено» снимает цель, «не выполнено» запускает следующий ход, «недостижимо» отменяет её. Контекст между ходами сохраняется. Отсюда требование к формулировке: цель — это **проверяемое состояние**, а не работа. «Реализуй проект» проверить нельзя; «стенд поднимается, тесты зелёные, линтер чист» — можно. Программа работ при этом живёт в `docs/plan.md`: цель отвечает на вопрос «когда закончили», план — «что делаем».

   **Существенное ограничение:** цель не меняет режим разрешений. В обычном режиме команда вне списка `allow` останавливает цикл и ждёт подтверждения человека — постройка не безнадзорна. Полная автономность достигается только в режиме `auto`.

**Пятый элемент, без которого рассыпаются остальные четыре, — материализация результатов в файлы.** План и результаты разведки, оставленные только в переписке, живут ровно до первого сжатия контекста. Постройка занимает десятки минут, за это время детали вымываются, и агент начинает достраивать решения по памяти вместо утверждённых. Поэтому:

| Результат | Куда сохраняется | Что даёт |
|-----------|------------------|----------|
| Утверждённый план | `docs/plan.md` | опора при долгой постройке, переживает сжатие контекста и перезапуск сессии, вычитывается человеком до старта, служит источником для ADR в блоке 10 |
| Разведка источника | `docs/research/catalog-source.md` | обоснование селекторов парсера; сохраняются **свои выводы, а не текст страниц** |
| Критерий готовности | внутри `docs/plan.md` | `/goal` ссылается на файл, а не перечисляет пункты в формулировке, которая сама подвержена сжатию |

**Практическая деталь:** в plan mode агент не может писать файлы — это режим только на чтение. Сохранение плана выполняется первым действием **после** выхода из режима.

**Принцип, который стоит проговорить как отдельный тезис:** контекст — рабочая память, репозиторий — долговременная. Всё, что должно пережить сессию, кладётся в файл. Это же объясняет, почему автономность агента растёт по мере накопления артефактов: план, правила, спецификации и тесты в репозитории снимают вопросы, которые иначе задавались бы заново в каждой сессии.

**Источник паттернов (назвать аудитории):** официальная библиотека промптов Claude Code — https://code.claude.com/docs/en/prompt-library — более 50 готовых промптов по фазам Discover → Design → Build → Ship → Operate, с разбором «почему это работает». Наш метод соответствует её ключевым паттернам: описывать результат, а не шаги; дать способ самопроверки; указывать образец; задавать измеримую цель; **вкладывать артефакт** (лог, ошибку, скриншот — вместо пересказа); задавать формат ответа. Ценность — в переносимых паттернах, а не в конкретных формулировках.

**Показ:** plan mode → разбор предложенного плана вслух (здесь же обсуждается выбор рантайма — материал будущего ADR) → наполнение каталога (разведка структуры, парсер, базовый скрипт наполнения — см. раздел «Наполнение каталога») → выход из режима → запуск `/goal`.

**Отдельный акцент на этапе разведки:** агент выходит в сеть встроенным `WebFetch`, минуя запрет `Bash(curl:*)`. Проговорить, почему это не пробел в границах, а корректная работа обоих правил (разбор — в описании этапа наполнения каталога и в заметках спикера). Здесь же уместно назвать честную границу применимости парсера: дисциплина запросов задана правилом `scraping.md`, но соблюдение её проверяет человек при ревью кода, а не harness.

**После запуска** постройка продолжается в фоне. Ведущий возвращается к прогрессу между блоками на 30–60 секунд.

**Проговорить главный паттерн работы с агентом:**

> Дайте агенту **проверку** — тесты, сборку, линтер, поднимающийся стенд. Без проверки циклом обратной связи становитесь вы и принимаете «выглядит готово» на веру. С проверкой агент итерирует сам.

## Блок 6. Субагенты (15 минут)

**Цель:** показать изоляцию контекста и специализацию исполнителей. Третья практика. Блок идёт, пока работает постройка.

**Формы агентности:**

1. **Встроенные субагенты** — `Explore` (поиск по коду) и `Plan` (проектирование), только чтение по построению; `general-purpose` — универсальный.
2. **Кастомные** — `.claude/agents/<имя>.md`: своя инструкция, набор инструментов, модель.
3. **Фоновые** — работают, не блокируя сессию.
4. **Параллельные сессии в git worktrees** — своя ветка и каталог на задачу.
5. **Облачные** — выполняются по расписанию, машина не нужна.
6. **Agent Teams** — экспериментальная функция, включается переменной окружения; расход токенов кратно выше, в живой демонстрации не используется.

**Ключевые положения:** субагент работает в изолированном контексте и возвращает только сводку — он может прочитать десятки файлов, а в основную сессию попадёт отчёт. Это основной способ экономии контекста. Субагент не видит переписку основной сессии: контекст задаётся его инструкцией и промптом запуска, поэтому в инструкции обязательно фиксируется формат отчёта.

**Безопасность:** субагентам-ревьюерам выдаются только инструменты чтения; право записи остаётся у основного агента, который запрашивает подтверждение.

**Субагент-писатель — отдельный разговор, и его стоит провести.** Ограничение «только чтение» относится к ревьюерам, а не к субагентам вообще: субагент может и реализовывать. Для этого в проекте заводится `implementer` — он получает инструменты записи и выполняет **один этап плана** от кода до коммита.

**Важно, когда именно он появляется.** Этот субагент **не создаётся заранее вместе с ревьюерами** — он создаётся в блоке 5, между парсером и скриптом наполнения, когда основная сессия заметно заполнилась деталями работы. Сначала показывается проблема (`/context` — что занимает окно), затем добавляется решение. Это живая иллюстрация принципа естественного наращивания, который мы декларируем в блоке 2: возможность добавляют, когда потребность стала наблюдаемой. Заготовленный заранее агент такой демонстрации не даёт.

**Первое задание исполнителя — скрипт наполнения.** Выбор не случаен: задача компактная, самодостаточная, результат проверяется одной командой. И возникает точная демонстрационная пара на соседних задачах: парсер выполняла основная сессия — виден каждый вызов инструмента; скрипт наполнения выполняет субагент — возвращается сводка. Обмен наблюдаемости на изоляцию контекста аудитория видит вживую, а не на слайде.

| | Выигрыш | Цена |
|---|---------|------|
| Реализация субагентом | основная сессия остаётся координатором и не заполняется деталями реализации | возвращается сводка, а не ход работы: меньше видно и труднее вмешаться |
| Реализация основной сессией | виден каждый шаг, легко поправить на ходу | контекст заполняется, план и соглашения вытесняются |

Границы для пишущего субагента задаются в его инструкции и продолжают действовать через общие permissions и hooks сессии: не трогать конфигурацию агента, не выполнять деструктивные команды, не отправлять изменения в удалённый репозиторий, при отказе в правах — сообщить, а не искать обход. Координация обеспечивается общим источником истины: субагент не видит переписку, но читает `docs/plan.md`.

**Про параллельность — честная граница применимости.** Параллелизм окупается на чтении: три ревьюера одновременно независимы и ничего не меняют. На записи он окупается только при действительно непересекающихся областях (разные сервисы в разных каталогах при зафиксированном в плане интерфейсе); общие файлы — `docker-compose.yml`, чарт — остаются за координатором. Несколько писателей в одной области дают конфликты и координационные издержки выше выигрыша. Штатный механизм для параллельной работы над независимыми задачами — git worktrees: своя ветка и каталог на задачу.

**Для занятия действует простое правило:** пока объясняем — работает основная сессия на виду; когда ушли в фон — делегируем. Аудитория должна увидеть агентный цикл, а не индикатор ожидания.

**Показ:** субагенты проекта — ревьюер кода, аудитор безопасности, ревьюер схемы БД. Запустить одного на уже созданной агентом части проекта.

**Практика участников (6 минут):** создать или скопировать субагента под свою роль и запустить в своём проекте. **Проверка:** получен отчёт с находками.

## Блок 7. Автономные режимы: /loop и периодические проверки (8 минут)

**Цель:** показать работу без постоянного участия человека.

| Механизм | Принцип | Применение в проекте |
|----------|---------|----------------------|
| `/goal` | до выполнения условия | доведение постройки до критерия готовности (запущено в блоке 5) |
| `/loop` | по времени, в открытой сессии | периодический прогон тестов и проверки безопасности по мере появления кода |
| `/schedule` | по расписанию в облаке | регулярный аудит без открытой сессии |
| headless `claude -p` | одна задача без интерактива | ревью изменений в GitHub Actions |

**Разграничение (повтор из карты):** hook — по событию, `/loop` — по времени, `/goal` — до условия, `/schedule` — по расписанию. Точнее: `/goal` начинает следующий ход, когда предыдущий завершился и условие не выполнено; `/loop` — когда истёк интервал. Отсюда и назначение: доведение задачи против дежурного наблюдения.

> **Не запускать `/loop` при активной цели.** Оба механизма управляют началом следующего хода, но по разным критериям; одновременная работа документацией не описана. В этом блоке команду **разбираем и показываем**, а запускаем после завершения постройки — в блоке 9 или 11 — либо в отдельной сессии.

**Показ:** запустить `/loop` с периодической проверкой — прогон тестов и аудит безопасности по мере готовности кода; показать job ревью на GitHub Actions (бесплатные runner'ы), где секрет аутентификации берётся из секретов репозитория, а права агента ограничены чтением.

**Аутентификация агента в CI — разобрать явно, это частый вопрос аудитории.** Два взаимоисключающих варианта: по подписке — секрет `CLAUDE_CODE_OAUTH_TOKEN`, полученный командой `claude setup-token` (выдаёт долгоживущий токен, его копируют вручную в секреты репозитория); по API — секрет `ANTHROPIC_API_KEY`. **Обе переменные одновременно задавать нельзя:** при наличии API-ключа он имеет приоритет, и подписка молча не используется. Прогоны по подписке расходуют её лимит и конкурируют с интерактивной работой, поэтому для регулярного ревью на каждый pull request предсказуемее отдельный API-ключ с собственным бюджетом; для учебного проекта достаточно подписки.

## Блок 8. Стоимость, токены и контекст (8 минут)

**Две модели оплаты:** подписка (Pro, Max, Team Premium, Enterprise) — фиксированная плата, общий лимит с веб-версией; API — оплата за токены, для автоматизации и CI. При наличии `ANTHROPIC_API_KEY` расход идёт по тарифам API.

**Автоматизация возможна и на подписке** (см. блок 7): команда `claude setup-token` выдаёт долгоживущий токен для CI. Различие не в том, «что можно», а в том, откуда списывается расход: подписка — фиксированная плата и общий лимит на всё, включая прогоны в CI; API — отдельный счёт с собственным бюджетом и без конкуренции с вашей интерактивной работой.

**Снижение стоимости:** prompt caching (чтение из кэша примерно вдесятеро дешевле ввода — существенно, поскольку системный промпт и CLAUDE.md не меняются между сообщениями); batch (−50 % для асинхронных задач); выбор модели под задачу — механические правки, повседневная работа и архитектурные решения требуют разных моделей.

**Контроль:** `/cost`, `/status`. **Живая демонстрация:** показать `/cost` текущей сессии и назвать реальную стоимость постройки проекта, измеренную на репетиции, — это самая убедительная цифра занятия.

**Расход контекста по возможностям:** CLAUDE.md — в каждом запросе; навыки — описания на старте, содержимое при использовании; MCP — имена на старте, описания при обращении; субагенты — изолированно; hooks — ноль. Практический вывод: объёмную работу выполняют субагенты.

## Блок 9. Ревью и документирование агентами (12 минут)

**Цель:** показать, что проверка и документирование результата — тоже работа агентов, выполняемая в изолированных контекстах.

**Показ — три параллельных проверки созданного проекта:**

1. **Ревью кода** — соответствие соглашениям проекта, качество, покрытие тестами.
2. **Аудит безопасности** — секреты, права контейнеров, зафиксированные версии, настройки GitHub Actions, конфигурация worker-режима.
3. **Ревью данных** — схема, миграции, индексы, обратимость.

Свести отчёты в один и оформить исправление найденного как отдельный коммит. Проговорить принцип: проверяющий не имеет права записи, исправляет основной агент.

**Документирование:** отдельным субагентом — README с инструкцией запуска стенда и описанием эндпоинтов. Отметить: документацию пишет тот, кто видит код целиком в свежем контексте, а не тот, кто утомлён длинной сессией постройки.

## Блок 10. ADR и архитектурная схема (10 минут)

**Цель:** зафиксировать архитектурные решения и подготовить проект к публикации.

**ADR (Architecture Decision Record)** — короткий документ на решение: контекст, рассмотренные варианты, выбор, последствия. Для нашего проекта решения содержательны:

- отказ от php-fpm и переход на рантайм с постоянными воркерами: что это даёт и чем оплачивается;
- выбор конкретного рантайма для каждого сервиса и сравнение вариантов;
- разделение на два сервиса и способ их взаимодействия;
- стратегия работы с данными и миграциями.

**Показ:** попросить агента создать ADR по принятым решениям, включая **честный раздел последствий** — постоянные воркеры требуют дисциплины в работе с состоянием между запросами, и агент обязан это зафиксировать.

**Архитектурная схема:** Mermaid-диаграмма в `docs/architecture.md` — GitHub рендерит её нативно, отдельные инструменты не нужны. Показать схему компонентов стенда и схему развёртывания в Kubernetes.

**Вывод блока:** документация и архитектурные решения — не приложение к проекту, а часть результата; агент способен создать их из кода, но качество зависит от заданных правил.

## Блок 11. Результат, обсуждение, внедрение (10 минут)

**Показ результата:** поднять стенд командой `docker compose up`, обратиться к эндпоинтам магазина — каталог с наполненной базой, поиск по книгам, оформление заказа, — показать историю коммитов, pull request с ревью, зелёный конвейер GitHub Actions, чарт, ADR и схему. Назвать затраченное время и стоимость.

**Обсуждение — вопросы, которые стоит задать аудитории:**

- Что из созданного вы приняли бы в свой репозиторий без правок, а что потребовало бы доработки?
- Где проходит граница ответственности: кто отвечает за код, написанный агентом?
- Какие правила вы бы добавили в конфигурацию, чтобы результат был ближе к вашим стандартам?

**Чек-лист внедрения:**

| Неделя | Шаг |
|--------|-----|
| 1 | `/init` и пять соглашений в CLAUDE.md |
| 2 | `deny` на секреты в `.claude/settings.json`, зафиксировать в репозитории |
| 3 | Один навык из самой частой повторяющейся инструкции |
| 4 | Субагент-ревьюер под свою роль; измерить `/cost` до и после |

**Plugins:** созданная конфигурация упаковывается в устанавливаемый набор — способ перенести стандарт на другие команды. Два живых примера из официального каталога (https://claude.com/plugins): **Superpowers** Джесси Винсента (более миллиона установок: брейншторминг требований, TDD-цикл, систематический дебаггинг, ревью против плана) и **mattpocock/skills** (устанавливается и как плагин с автообновлением, и копированием файлов в репозиторий для полного контроля — само это различие поучительно). То, что мы собрали сегодня, устроено так же — и может быть опубликовано так же.

**Замечание по безопасности при установке чужих наборов:** плагин и навык — это инструкции, которые будут управлять вашим агентом, и код hooks, который будет исполняться. Читать перед установкой — так же, как читают чужой код перед подключением зависимости.

## Подготовка к воркшопу

- **Плейбук `PROMPTS.md`** — основной рабочий документ: промпты по блокам в формате «промпт → ожидаемый результат → проверка → запасной вариант».
- **Эталонный репозиторий** — результат полного прогона плейбука на репетиции: источник запасных файлов при сбоях, раздатка участникам и материал для блока 0.
- Полный прогон на репетиции обязателен: замерить время постройки и стоимость, записать вывод для запасных вариантов.
- Проверить: Docker запускается и порты свободны; образы предварительно загружены; GitHub MCP авторизован; значение `ANTHROPIC_API_KEY` соответствует нужному счёту.
- Подготовить пустой репозиторий на GitHub с включёнными Actions.
- Решить вопрос с наполнением каталога заранее (см. раздел «Наполнение каталога»): подготовить описание модели данных для генерации наполнения либо выбранный открытый набор.

## Рекомендации по проведению

- Тайминг — ориентир. При высокой вовлечённости увеличивать время на практики, сокращая теоретические блоки.
- Постройка идёт в фоне: возвращаться к прогрессу между блоками, но не ждать её у экрана.
- При сбое живой демонстрации переключаться на запасной вариант в течение 60–90 секунд, не пытаясь чинить в эфире.
- Вопросы, уводящие в сторону, фиксировать и разбирать в блоке 11.
- Agent Teams — только упоминание на слайде.
