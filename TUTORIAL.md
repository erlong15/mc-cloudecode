# Туториал: работа с Claude Code

Конспект воркшопа и самостоятельный справочник. Остаётся у вас: терминология,
устройство агента, приёмы ежедневной работы, шпаргалка команд и рецепты типовых
задач с готовыми командами.

Примеры приведены на материале проекта OhMyClaude Books — книжного магазина
на Laravel, который создаётся на воркшопе. Эталонная конфигурация, на которую
ссылается текст, лежит в `reference-config/`.

---

## 1. Терминология

| Термин | Что это |
|--------|---------|
| **Модель** | Нейросеть (Opus, Sonnet, Haiku), которая умеет ровно одно: читать текст и порождать текст, включая запросы на вызов инструментов. Не запускает команды, не читает файлы, ничего не помнит между запросами (stateless). |
| **Harness** | «Обвязка» вокруг модели — сам Claude Code. Собирает каждый запрос, ведёт цикл, исполняет инструменты, проверяет права, управляет контекстом. |
| **Агент** | Модель + harness. Система, которая получает задачу и сама доводит её до результата через цикл действий. |
| **Инструмент (tool)** | Действие, которое harness умеет выполнять по запросу модели: `Read` (чтение файла), `Write`/`Edit` (запись), `Bash` (команда), `Grep`/`Glob` (поиск) и другие. |
| **Контекст (окно контекста)** | Всё, что модель «видит» в одном запросе: системный промпт, CLAUDE.md, описания инструментов, история диалога с результатами. Ограничен (~200 000 токенов) — это главный дефицитный ресурс. |
| **Токен** | Единица измерения текста (~3–4 символа). Оплата API и лимиты подписки считаются в токенах. |
| **CLAUDE.md** | Память проекта: файл, который harness кладёт в каждый запрос. Соглашения, ограничения, структура. |
| **Rule** | Файл в `.claude/rules/` с glob-паттернами `paths` во frontmatter — подгружается в контекст только при работе с соответствующими файлами. |
| **Skill** | Переиспользуемая инструкция в `.claude/skills/<имя>/SKILL.md`. Вызывается вручную (`/имя`) или автоматически по описанию. В контексте на старте — только описание. |
| **Субагент** | Отдельный исполнитель со своим окном контекста. Читает хоть 50 файлов — в основную сессию возвращается только итоговая сводка. Задаётся файлом `.claude/agents/<имя>.md`. |
| **MCP** | Model Context Protocol — стандарт подключения внешних систем (GitHub, БД, Slack): сервер отдаёт агенту дополнительные инструменты. |
| **Permissions** | Правила доступа в `settings.json`: `deny` / `ask` / `allow`. Проверяются harness'ом на каждый вызов инструмента, первое совпадение выигрывает. |
| **Hook** | Скрипт, который harness запускает по событию (`PreToolUse`, `PostToolUse`, …). Выполняется всегда, независимо от «мнения» модели. Exit code 2 = заблокировать действие. |
| **Plugin** | Упаковка Skills, hooks, агентов и MCP-серверов в один устанавливаемый набор — для переноса настройки между командами. |
| **Headless-режим** | `claude -p "<задача>"` — одна задача без интерактива, результат в stdout (`--output-format json`). Способ запускать агента из CI. |
| **Plan mode** | Режим «только чтение»: агент изучает код и предлагает план, но не меняет файлы. Вход/выход — Shift+Tab. |
| **Checkpoint** | Контрольная точка: каждый ваш промпт сохраняет состояние разговора и файлов; `/rewind` откатывает к любой из них. Внешние эффекты (деплой, БД) не откатываются. |
| **Prompt caching** | Кэширование неизменной части запроса (системный промпт, CLAUDE.md): повторное чтение из кэша ~в 10 раз дешевле обычного ввода. |

## 2. Как устроен один шаг агента

```
ваша задача
   │
   ▼
модель читает контекст и решает: нужен инструмент
   │
   ▼
harness перехватывает вызов:
   PreToolUse hook  ──может заблокировать (exit 2)
   permissions      ──deny → отказ / ask → вопрос вам / allow → дальше
   │
   ▼
инструмент выполняется, результат кладётся в контекст
   PostToolUse hook ──например, запуск gitleaks после записи
   │
   ▼
модель читает результат → следующий инструмент … → финальный ответ
```

Два следствия, на которых строится вся настройка:

- **Просьба живёт в модели** (CLAUDE.md, Skill) — модель старается её учитывать,
  но может забыть. **Правило живёт в harness** (permissions, hook) — срабатывает всегда.
- Всё, что попадает в контекст, конкурирует за одно окно. Объёмную работу
  отдавайте субагентам, справочное знание — в Skills (грузятся лениво).

## 3. Приёмы ежедневной работы

Это база, которая работает до всяких расширений — и вместе с ними.

- **Plan mode.** Для нетривиальных задач начинайте в режиме планирования
  (Shift+Tab или `claude --permission-mode plan`): агент читает и предлагает план,
  но не меняет файлы. Одобрили план — вышли из режима и реализуете.
  Канонический цикл: **изучить → спланировать → реализовать → закоммитить**.
- **Конкретный промпт.** Не «добавь тесты», а «напиши тест для оформления заказа
  на случай пустой корзины; без моков; образец — `tests/Feature/CartTest.php`».
  Файлы указывайте через `@путь/к/файлу` — агент прочитает их до ответа.
- **Цель, а не шаги.** Не диктуйте «открой X, потом запусти Y» — сформулируйте
  цель («разберись, почему падает деплой»), инструменты агент выберет сам.
- **Глубина размышления по задаче.** Аудит, архитектура, поиск первопричины —
  попросите подумать глубже (`ultrathink` в промпте или повышенный `/effort`).
  Механические правки — обычный режим, он быстрее и дешевле.
- **Коррекция курса — сразу.** Агент пошёл не туда — жмите Esc и поправляйте,
  не дожидаясь конца хода. `/rewind` (или двойной Esc) откатывает к контрольной
  точке: разговор, файлы или всё вместе — каждый ваш промпт создаёт checkpoint.
  Важно: checkpoint не отменит внешние эффекты (деплой, миграцию БД) — для этого
  git и бэкапы.
- **Гигиена контекста.** `/clear` между несвязанными задачами; `/compact` с
  указанием, что сохранить. Длинная замусоренная сессия = потерянные инструкции.
- **Модель под задачу.** `/model`: haiku — механика и переименования, sonnet —
  повседневная работа, opus — архитектура и сложные решения. В субагентах модель
  фиксируется в frontmatter (у наших ревьюеров — `sonnet`).
- **Данные через stdin.** `cat error.log | claude -p "объясни первопричину"` —
  быстрее, чем пересказывать проблему словами.
- **Диагностика.** `/doctor` проверяет установку и настройку;
  CLI-утилиты (`gh`, `kubectl`, `psql`) агент использует сам — они ему доступнее
  и дешевле по контексту, чем пересказ их вывода.

## 4. Шпаргалка команд

| Команда | Что делает |
|---------|-----------|
| **Управление сессией** | |
| `/clear` | очистить контекст (между несвязанными задачами) |
| `/compact [фокус]` | сжать историю, сохранив главное |
| `/rewind` | откат к контрольной точке: разговор, файлы или всё |
| `/resume` | вернуться к прошлой сессии |
| `/model` | сменить модель (haiku / sonnet / opus) |
| `/cost`, `/status` | расход токенов и состояние сессии |
| **Настройка** | |
| `/init` | сгенерировать CLAUDE.md по репозиторию |
| `/permissions` | интерактивное управление правами |
| `/mcp` | состояние MCP-серверов и их расход токенов |
| `/agents` | управление субагентами |
| `/hooks` | управление hooks |
| `/doctor` | диагностика установки и настройки |
| `/config` | общие настройки |
| **Работа** | |
| `/goal <условие>` | повторять работу до выполнения условия (`/goal clear` — снять) |
| `/loop [интервал]` | повторять по времени (локально) |
| `/schedule` | облачные задачи по расписанию |
| `/code-review`, `/security-review`, `/debug` | встроенные skills |
| **В строке ввода** | |
| `! <команда>` | выполнить shell-команду напрямую |
| `@путь/к/файлу` | вложить файл в промпт |
| Shift+Tab | переключить plan mode |
| Esc | прервать агента и поправить курс |

## 5. Рецепты типовых задач

### Рецепт 1. Разобраться в незнакомом проекте

**Подход:** не читать код самому — заставить агента построить карту.

```
Изучи этот репозиторий и объясни: что это за проект, как он собирается,
где точки входа и что здесь самое рискованное при изменениях
```

Затем — точечные вопросы: «покажи, откуда берётся тег образа», «кто пишет в таблицу
books». Для большого репозитория просите использовать субагента (`Explore`) — карта
вернётся сводкой, не съев контекст. Если проекта ещё нет в Claude Code — начните
с `/init`: агент сам составит первичный CLAUDE.md.

### Рецепт 2. Внести изменение и довести до зелёного состояния

**Подход:** изучить → спланировать → реализовать → проверить; финал — через `/goal`.

1. Начните в plan mode: агент изучает код и предлагает план, ничего не меняя.
   Одобрили — выходите из режима.
2. Сформулируйте изменение с проверяемым критерием готовности
   (по возможности — сначала падающий тест, потом реализация):
   ```
   Добавь в таблицу books поле published_at. Миграция должна пройти проверку db-reviewer
   ```
3. Просмотрите diff (агент показывает изменения до записи — читайте их).
4. Доведите до критерия автоматически:
   ```
   /goal тесты проходят и в отчёте db-reviewer нет находок
   ```
   Агент будет исправлять и перепроверять, пока условие не выполнится. Остановить: `/goal clear`.

### Рецепт 3. Ревью изменений перед мержем

**Подход:** чеклист — в Skill, исполнение — read-only субагенту.

```
Используй субагента pr-reviewer для проверки текущих изменений
```

или вручную по чеклисту: `/project-review`. Субагент не имеет прав записи
(`tools: Read, Grep, Glob`) — он физически не может «поправить заодно».
Право изменять остаётся у основного агента, который спрашивает вас.

### Рецепт 4. Проверить миграцию БД

**Подход:** правила — в `.claude/rules/database.md` (подгружаются при работе с `db/**`),
проверка — субагентом.

```
Используй субагента db-reviewer для проверки миграций каталога
```

Отчёт: находка → файл и строка → чем грозит в промышленной эксплуатации →
рекомендация → вердикт. Типовые находки: `UPDATE` без `WHERE`, индекс без
`CONCURRENTLY`, отсутствие секции отката, внешний ключ без индекса.

### Рецепт 5. Найти секреты и проблемы безопасности

**Подход:** три эшелона.

1. Разовая проверка: субагент `security-auditor` или встроенный `/security-review`.
2. Автоматика на каждое изменение: PostToolUse-hook с gitleaks (уже настроен
   в `.claude/settings.json` — сработает при любом Edit/Write).
3. Защита от чтения: `deny: ["Read(**/.env)", "Read(**/*.key)"]` — агент даже
   не увидит содержимое секретов.

### Рецепт 6. Настроить границы для агента

**Подход:** от запретов к разрешениям, по нарастающей.

1. `deny` — что нельзя никогда: чтение секретов, `sudo`, сетевые загрузки.
2. `ask` — что требует подтверждения: `git push`, деплой.
3. `allow` — что можно без вопросов: тесты, линтеры, сборка.
4. То, что должно проверяться сложнее, чем шаблоном имени команды, — в PreToolUse-hook
   (см. `.claude/hooks/check-command.sh`: разбирает команду и блокирует по шаблонам).

Проверка настройки: попросите агента сделать запрещённое — «прочитай .env»,
«выполни curl» — и убедитесь, что harness отказал. Файл `.claude/settings.json`
коммитится в репозиторий — границы приезжают всей команде вместе с кодом.

### Рецепт 7. Автоматизировать: по времени, по условию, в CI

| Задача | Инструмент | Пример |
|--------|-----------|--------|
| Доделать до условия | `/goal` | `/goal все тесты проходят` |
| Повторять по времени (локально) | `/loop` | `/loop 10m проверь статус pipeline` |
| По расписанию в облаке | `/schedule` | еженедельный аудит зависимостей |
| На каждый pull request | headless в CI | `.github/workflows/claude-review.yml` |

Headless-минимум для CI:

```bash
claude -p "Проверь изменения по чеклисту project-review, верни нарушения списком" \
  --allowedTools "Read,Grep,Glob" \
  --output-format json
```

Ключ — из секретов CI (`ANTHROPIC_API_KEY`), права — только чтение. Агент с правом
записи в CI — отдельное решение: сначала договоритесь, кто отвечает за его коммиты.

Тот же headless — для массовой обработки (fan-out): список целей → цикл:

```bash
for f in $(cat files.txt); do
  claude -p "Проверь $f по чеклисту project-review" --allowedTools "Read,Grep,Glob"
done
```

А для параллельной работы над **разными** задачами на одной машине — git worktrees:
`git worktree add ../fix-auth` и отдельная сессия Claude в каждом каталоге;
ветки разные, файлы не конфликтуют.

### Рецепт 8. Держать контекст и стоимость под контролем

- `/cost` — сколько потратила текущая сессия; `/status` — состояние и лимиты.
- `/context` или `/mcp` — что занимает окно контекста.
- Качество ответов в длинной сессии снизилось — `/compact` (сжать историю) или `/clear` + краткое
  восстановление задачи; важное к этому моменту должно жить в CLAUDE.md, а не в истории чата.
- Объёмные чтения — субагентам: в основное окно возвращается только сводка.
- Три параллельных агента за час тратят примерно как одиночная сессия за день —
  замеряйте `/cost` до и после изменений в процессе.

## 6. Rules в деталях

`.claude/rules/` — это способ масштабировать память проекта, не раздувая CLAUDE.md.

- **Без `paths`** во frontmatter правило действует всегда — как продолжение
  CLAUDE.md, разложенное по тематическим файлам.
- **С `paths`** правило подгружается только при работе с совпавшими файлами:

  ```markdown
  ---
  paths:
    - "db/**"
    - "**/*.sql"
  ---
  ```

  Glob-синтаксис: `**` — любая глубина, `*.{sql,py}` — brace expansion.
- **Личный уровень** — `~/.claude/rules/`: правила разработчика для всех его
  проектов; проектные и личные правила дополняют друг друга.
- **Рабочее разделение трёх механизмов:** CLAUDE.md — короткое ядро (карта проекта,
  универсальные соглашения) · rules — тематические своды по областям · Skills —
  процедуры и справка по запросу.
- **Типичная ошибка:** правило есть, а агент его «не видит» — редактируемый файл
  не попадает под glob. Проверяйте паттерн на реальном пути файла.
- В эталонной конфигурации шесть правил: `laravel.md`, `octane.md`,
  `containers.md`, `database.md`, `helm.md`, `github-actions.md` — откройте
  любое как образец.

## 7. Hooks в деталях

Hook — произвольный код, который harness выполняет по событию. Это не просьба
к модели, а программа: срабатывает всегда.

**События:**

| Событие | Когда | Типовое применение |
|---------|-------|--------------------|
| `PreToolUse` | перед вызовом инструмента | блокировка опасных команд, валидация |
| `PostToolUse` | после успешного вызова | линтер/автоформат после Edit, поиск секретов |
| `UserPromptSubmit` | при отправке промпта | добавить контекст (ветка, тикет) или заблокировать промпт |
| `SessionStart` | старт/возобновление сессии | подгрузить окружение и состояние |
| `Stop` | агент завершает ход | проверка полноты: не дать остановиться раньше времени |

**Механика:**

- `matcher` — regex по имени инструмента (`Bash`, `Edit|Write`); пустой — все.
- На stdin приходит JSON: `session_id`, `tool_name`, `tool_input`
  (у `PostToolUse` — ещё и результат вызова). Разбирайте через `jq`.
- **Каналы вывода:** exit 0 — разрешено (у `UserPromptSubmit`/`SessionStart`
  stdout добавляется в контекст) · **exit 2 — заблокировано**, stderr уходит
  модели, и она перестраивается · тонкое управление — JSON-ответ
  с `permissionDecision: "deny" | "ask" | "allow"`.
- Долгие проверки — задавайте `timeout`; отладка срабатываний — `claude --debug`.

**Гигиена:** hook выполняется с вашими правами — это код, и ревьюится как код.
Храните скрипты в репозитории (`.claude/hooks/`), в конфиге ссылайтесь через
`${CLAUDE_PROJECT_DIR}`. Формат hooks меняется чаще других — сверяйте с документацией.

**Идеи типовых hooks:** автоформат после каждого Edit (`pint`);
запрет Edit для прод-конфигов; gitleaks после Write (настроен здесь);
уведомление в Slack по `Stop`; подстановка номера тикета из ветки
в `UserPromptSubmit`. Рабочий пример разобран в `.claude/hooks/check-command.sh`.

## 8. Принципы, которые стоят за рецептами

1. **Контекст и границы.** Всякая настройка отвечает на один из двух вопросов:
   что агент знает (CLAUDE.md, rules, Skills, MCP) или что ему можно
   (permissions, hooks). Если непонятно, куда класть правило, — задайте себе этот вопрос.
2. **Просьба против правила.** Должно соблюдаться всегда → harness (deny, hook).
   Достаточно «по умолчанию так» → модель (CLAUDE.md, Skill).
3. **Дайте агенту проверку — это главный паттерн.** Задача с проверяемым критерием
   (тест, сборка, линтер, отчёт ревьюера) позволяет агенту итерировать самому —
   `/goal`, hook, тесты. Без проверки циклом обратной связи становитесь вы,
   и «выглядит готово» приходится принимать на веру. Требуйте доказательств:
   вывод тестов, отчёт, diff — не утверждение «сделано».
4. **Ревьюеры — только чтение.** Проверяющий субагент не должен уметь исправлять:
   разделение ролей сохраняет контроль за человеком.
5. **Естественный порядок наращивания.** Не настраивайте всё сразу. Claude дважды
   ошибся → строка в CLAUDE.md. Инструкцию вставляете второй раз → Skill. Контекст
   переполняется → субагент. Правило нарушено хоть раз → hook. Настройка нужна
   соседней команде → plugin.
6. **Конфигурация — на английском.** CLAUDE.md, rules, skills, инструкции агентов
   читает модель: на английском они работают надёжнее и дешевле по токенам.
   Разговаривать с агентом в чате можно по-русски.
7. **Маленькие шаги.** Одно изменение → просмотр diff → проверка → следующее.
   Большая задача одним промптом = большой diff, который никто не прочитает.
