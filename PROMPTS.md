# Плейбук промптов воркшопа

Основной рабочий документ ведущего: последовательность промптов, которыми агентная
система создаётся и запускается в прямом эфире. Формат каждого шага:
**промпт → ожидаемый результат → проверка → запасной вариант**.

Промпты агенту формулируются по-русски. Файлы конфигурации (`CLAUDE.md`,
`.claude/**`) агент создаёт на английском языке: их читает модель. Это различие
следует проговорить аудитории.

Методический приём, который также стоит обозначить: конфигурацию агента создаёт
сам агент — по одному промпту на артефакт. Человек проверяет и правит результат.

> **Технический стек выверен по официальным источникам 17.08.2026.** Версии
> изменяются; перед проведением требуется повторная сверка. Проверенные сведения
> сведены в приложении и встроены в промпты, чтобы агент не выбирал стек
> самостоятельно.

## Этап 0. Пустой репозиторий (выполняется до эфира)

Выполняется вручную. Вариант А — одной командой через `gh` (создаёт, клонирует
и привязывает remote):

```bash
gh repo create ohmyclaude-books --public --clone
cd ohmyclaude-books
git commit --allow-empty -m "Initial commit"
git push -u origin main
```

Вариант Б — репозиторий создан через веб-интерфейс GitHub; тогда клонировать
и инициализировать ветку вручную:

```bash
git clone git@github.com:<логин>/ohmyclaude-books.git
cd ohmyclaude-books
git commit --allow-empty -m "Initial commit"
git push -u origin main
```

Пустой коммит нужен, чтобы ветка `main` существовала до первых коммитов агента.
Вся дальнейшая работа — в этом локальном клоне: Claude Code запускается
в каталоге репозитория.

**Проверить состояние GitHub Actions** (в новом публичном репозитории личного
аккаунта они включены по умолчанию; отключёнными бывают в организациях
с политиками): Settings → Actions → General → «Allow all actions and reusable
workflows». Смысл проверки: workflow, который агент закоммитит в конце
постройки, должен реально запускаться.

**Заранее для этапа 5 — аутентификация агента в CI.** Два взаимоисключающих
варианта; секрет добавляется в Settings → Secrets and variables → Actions.

| Способ оплаты | Секрет в репозитории | Как получить |
|---------------|----------------------|--------------|
| Подписка (Pro/Max/Team) | `CLAUDE_CODE_OAUTH_TOKEN` | локально `claude setup-token` |
| API (оплата за токены) | `ANTHROPIC_API_KEY` | ключ из консоли Anthropic |

Команда `claude setup-token` открывает браузер для авторизации и выдаёт
долгоживущий токен (порядка года). Токен **не сохраняется автоматически** —
скопировать сразу и положить в секреты репозитория.

**Существенные оговорки для подписки в CI:**

- Прогоны в CI расходуют **лимит вашей подписки** и конкурируют за него
  с интерактивной работой. Для регулярного ревью на каждый pull request это
  ощутимо; для учебного проекта и разовых демонстраций — приемлемо.
- **Не задавать обе переменные одновременно:** при наличии `ANTHROPIC_API_KEY`
  он имеет приоритет, и OAuth-токен будет проигнорирован — оплата молча уйдёт
  по API. В workflow для подписки `ANTHROPIC_API_KEY` не устанавливать вовсе.
- Токен предназначен для inference; функции, требующие полноценного входа
  в аккаунт (удалённое управление, коннекторы claude.ai), через него
  недоступны — для CI это не ограничение.

## Этап 1 · Блок 2. Память и правила проекта

Все дальнейшие шаги выполняются в сессии Claude Code, запущенной **в корне
локального клона репозитория** (`cd ohmyclaude-books && claude`). Файлы
конфигурации агент создаёт сам по указанным путям; проверять их появление
удобно командой `ls -R .claude` или в редакторе.

Итоговая структура после этапов 1 и 2:

```
ohmyclaude-books/
├── CLAUDE.md                  ← шаг 1.1
└── .claude/
    ├── rules/*.md             ← шаг 1.2 (семь файлов)
    ├── skills/project-review/SKILL.md   ← шаг 1.3
    ├── agents/*.md            ← шаг 1.4 (три файла)
    ├── settings.json          ← шаг 2.1 (вручную)
    └── hooks/check-command.sh ← шаг 2.2
```

### 1.1. CLAUDE.md

```
Мы начинаем новый проект: книжный магазин OhMyClaude Books.

Целевая архитектура:
- два сервиса на Laravel 13 (PHP 8.4), оба под Laravel Octane 2.x без php-fpm:
  services/catalog — каталог книг (авторы, серии, жанры, теги, поиск),
    рантайм FrankenPHP;
  services/orders — корзина и заказы, рантайм RoadRunner;
- PostgreSQL — по базе на сервис; Redis — кэш и очереди;
- локальный стенд через docker-compose;
- Helm-чарт в charts/ для развёртывания в Kubernetes;
- CI на GitHub Actions;
- тесты на Pest.

Создай CLAUDE.md — короткое ядро памяти проекта: карта репозитория,
универсальные соглашения (порядок работы, стиль коммитов, обязательные
проверки перед коммитом), ограничения (секреты не коммитим, деструктивные
команды не выполняем), порядок ревью изменений.

Не дублируй в CLAUDE.md тематические правила по областям — для них мы заведём
.claude/rules/ следующим шагом; сошлись на них одной строкой.
Объём — до 60 строк. Пиши по-английски.
```

**Ожидаемый результат:** краткий `CLAUDE.md` без дублирования будущих правил.
**Проверка:** файл прочитывается за минуту, деталей об Octane и Helm в нём нет.
**Запасной вариант:** эталонный `CLAUDE.md`.

### 1.2. Правила по областям

```
Создай в .claude/rules/ тематические правила с frontmatter paths, чтобы каждое
подгружалось только при работе со своими файлами. Пиши по-английски.

1) laravel.md — paths: services/**/*.php
   Laravel 13, PHP 8.4. Строгая типизация, form requests для валидации,
   ресурсы для сериализации ответов, бизнес-логика вне контроллеров.
   Тесты на Pest, каталоги tests/Feature и tests/Unit.

2) octane.md — paths: services/**/*.php, services/**/Dockerfile
   Приложение работает под Octane в worker-режиме и живёт между запросами.
   Обязательные ограничения:
   - не инжектить в конструкторы синглтонов контейнер, Request или Config;
     использовать bind() вместо singleton() либо получать зависимости в методе;
   - глобальные хелперы app(), request(), config() безопасны;
   - запрещены статические свойства, накапливающие данные между запросами:
     это утечка памяти;
   - не использовать Octane::concurrently(), ticks и cache-драйвер octane —
     они работают только на Swoole, а проект использует FrankenPHP и RoadRunner;
   - в продакшн-конфигурации обязателен --max-requests для плановой
     перезагрузки воркеров и octane:reload после развёртывания.

3) containers.md — paths: **/Dockerfile, docker-compose.yml
   Базовые образы фиксируются по точному тегу, тег latest запрещён.
   FrankenPHP: dunglas/frankenphp:1.12.7-php8.4-trixie, расширения через
   install-php-extensions, обязательны pcntl (требование Octane) и pdo_pgsql.
   RoadRunner: php:8.4-cli с копированием бинарника
   COPY --from=ghcr.io/roadrunner-server/roadrunner:2025.1.15.
   Запуск от непривилегированного пользователя; порт не ниже 1024, чтобы
   не выдавать capabilities; права на storage/ и bootstrap/cache для этого
   пользователя. Секреты в образ не копируются.

4) database.md — paths: services/**/database/**, **/*.sql
   Каждая миграция обратима. UPDATE и DELETE только с WHERE.
   Индексы на существующих таблицах — CREATE INDEX CONCURRENTLY.
   Внешние ключи с индексами. Денежные суммы — NUMERIC(12,2)
   с CHECK (>= 0). Временные метки — timestamptz. Пароли — только хэши.

5) helm.md — paths: charts/**
   securityContext обязателен: runAsNonRoot, allowPrivilegeEscalation: false,
   capabilities drop ALL, readOnlyRootFilesystem где применимо.
   resources.requests и limits обязательны. Образ указывается по тегу
   или digest, latest запрещён. Секреты — через Secret, не в values
   открытым текстом. Обязательны liveness- и readiness-пробы.

6) scraping.md — paths: tools/catalog-parser/**
   Парсер каталога — локальный инструмент разработчика.
   Запросы: проверять robots.txt, не чаще одного запроса в секунду, backoff
   на 429 и 5xx, описательный User-Agent, запросы через HTTP-клиент приложения,
   а не через shell, кэш ответов локально.
   Данные: выгрузка в storage/catalog/ и только туда — этот каталог в .gitignore,
   спарсенный контент в репозиторий не коммитим. Собираем структурные
   метаданные (название, автор, серия, жанры, теги, цена, рейтинг),
   обложки и полные аннотации не сохраняем.
   Коммитится синтетический сидер (Laravel Seeder), работающий без парсера, чтобы проект
   запускался у любого, кто склонировал репозиторий.
   Селекторы разметки — в одном документированном месте; тесты — на сохранённых
   HTML-фикстурах, не на живых запросах.

7) github-actions.md — paths: .github/workflows/**
   Права токена задаются явно блоком permissions по минимуму.
   Сторонние actions фиксируются; official actions/* — минимум
   по мажорному тегу. Триггер pull_request_target с checkout кода
   из pull request запрещён. Данные из контекста события не подставляются
   в run напрямую — только через env, иначе возможна инъекция.
   Секреты передаются только через secrets.
```

**Ожидаемый результат:** семь файлов правил с корректным `paths`.
**Проверка:** открыть любой `.php` и запросить изменение — агент ссылается
на ограничения worker-режима без напоминания.
**Запасной вариант:** эталонный каталог `.claude/rules/`.

```
Создай в .claude/agents/ трёх субагентов, все только на чтение

1) code-reviewer — ревью кода Laravel: соответствие правилам проекта,
```

## Этап 2 · Блок 3. Границы (до запуска постройки)

### 2.1. Права доступа — файл `.claude/settings.json`

Создаётся **вручную, а не промптом**: это практика участников, и содержимое
границ человек должен осознанно написать сам. Тот же шаблон направляется в чат
участникам, чтобы они повторили у себя.

**Где:** в корне репозитория проекта, рядом с `CLAUDE.md`:

```
ohmyclaude-books/
├── CLAUDE.md
└── .claude/
    ├── rules/            ← создано на этапе 1
    ├── skills/           ← создано на этапе 1
    ├── agents/           ← создано на этапе 1
    ├── settings.json     ← создаём сейчас
    └── hooks/            ← появится на шаге 2.2
```

Создать каталог и открыть файл:

```bash
mkdir -p .claude
$EDITOR .claude/settings.json
```

Содержимое (шаблон для чата):

```json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "deny": [
      "Read(**/.env)",
      "Read(**/*.key)",
      "Bash(sudo:*)",
      "Bash(curl:*)",
      "Bash(wget:*)"
    ],
    "ask": [
      "Bash(git push:*)",
      "Bash(docker compose down:*)"
    ],
    "allow": [
      "Bash(composer:*)",
      "Bash(php artisan:*)",
      "Bash(./vendor/bin/pest:*)",
      "Bash(docker compose up:*)",
      "Bash(docker compose logs:*)",
      "Bash(helm lint:*)",
      "Bash(helm template:*)",
      "Bash(git add:*)",
      "Bash(git commit:*)"
    ],
    "defaultMode": "default"
  }
}
```

**Проверка шага:** файл сохранён, `/permissions` в сессии показывает новые
правила (перезапуск не нужен — настройки применяются на лету). Если правила
не появились — проверить, что JSON валиден: `python3 -m json.tool .claude/settings.json`.

**Почему `settings.json`, а не `settings.local.json`:** этот файл коммитится
в репозиторий и приезжает всей команде с `git clone`. Личные послабления
разработчик кладёт в `settings.local.json`, который в `.gitignore`.

### 2.2. Hook — этот файл уже пишет агент

В отличие от прав доступа, hook — это код, и его создание удобно поручить агенту:

```
Создай PreToolUse-hook для Bash: скрипт .claude/hooks/check-command.sh,
который читает JSON со stdin, извлекает .tool_input.command через jq
и блокирует опасные шаблоны — sudo, curl, wget, rm -rf /, chmod 777,
git push --force, --no-verify, включая случаи, когда шаблон находится
после && или |. При блокировке: exit 2 и объяснение в stderr.
Подключи через ${CLAUDE_PROJECT_DIR} в settings.json.
Добавь PostToolUse на Edit|Write: запуск gitleaks, если он установлен.
Протестируй скрипт вручную на блокируемой и на разрешённой команде.
```

**Проверка этапа — три случая в живой сессии:**

| Запрос агенту | Ожидаемая реакция | Что сработало |
|---------------|-------------------|---------------|
| `прочитай .env` | отказ, файл не прочитан | `deny` в settings.json |
| `выполни curl https://example.com` | блокировка с объяснением, агент перестраивается | PreToolUse-hook |
| `сделай git push` | запрос подтверждения | `ask` в settings.json |

Дополнительно — прямая проверка скрипта, минуя агента:

```bash
echo '{"tool_input":{"command":"cd services && git push --force"}}' \
  | .claude/hooks/check-command.sh; echo "exit=$?"   # ожидается 2
```

**Обоснование порядка блоков для аудитории:** далее агент строит проект несколько
десятков минут при минимальном надзоре. Границы должны быть установлены до начала
этой работы.

## Этап 3 · Блок 4. Подключение MCP

**Подключение выполняется до эфира.** Сервер GitHub **не поддерживает
динамическую регистрацию клиента**, поэтому обычный OAuth-поток завершается
ошибкой `Incompatible auth server: does not support dynamic client registration`.
Аутентификация — токеном в заголовке:

```bash
claude mcp add --transport http github https://api.githubcopilot.com/mcp/ \
  --header "Authorization: Bearer <GITHUB_TOKEN>"
```

Быстрый вариант токена, если авторизован `gh` (нужен scope `repo`):
подставить `$(gh auth token)` вместо `<GITHUB_TOKEN>`.

**Рекомендуемый вариант — отдельный fine-grained токен**, ограниченный одним
демонстрационным репозиторием (Settings → Developer settings → Fine-grained
tokens; права Contents, Issues, Pull requests). Причина, которую стоит
проговорить аудитории: токен сохраняется **открытым текстом** в `~/.claude.json`,
а команда попадает в историю оболочки. Токен, ограниченный одним репозиторием,
ограничивает и последствия его утечки. Это тот же принцип минимальных
привилегий, который мы применяли к субагентам и permissions, — теперь
применённый к самому инструменту.

**Область видимости:** по умолчанию сервер прописывается для текущего проекта.
Флаг `-s user` делает его доступным во всех проектах.

**Если подключение не удалось** — этап пропускается без последствий для
постройки: `claude mcp remove github`, дальше работаем локально.

Затем:

```
Через GitHub MCP создай в репозитории issue «Построить книжный магазин
OhMyClaude Books» с кратким описанием целевой архитектуры из CLAUDE.md
и перечнем этапов работ.
```

**Проверка:** `/mcp` отображает сервер подключённым, issue создан в репозитории.
**Запасной вариант:** пропустить MCP и работать локально; на последующие этапы
это не влияет.

## Этап 4 · Блок 5. Постановка задачи и запуск постройки

### 4.1. План до кода (plan mode, Shift+Tab)

```
Спроектируй реализацию проекта по CLAUDE.md и правилам из .claude/rules/.
Требуется план, а не код.

Опиши:
- структуру репозитория и границы между сервисами;
- модель данных каталога: книги, авторы, серии, жанры, теги и связи;
- API обоих сервисов и способ их взаимодействия;
- устройство локального стенда и способ проверки его работоспособности;
- порядок работ по этапам с точками коммитов;
- отдельно: чем FrankenPHP и RoadRunner различаются по модели работы,
  почему для каталога выбран первый, а для заказов второй, и какие
  ограничения worker-режима это накладывает на код.

Последний пункт станет основой ADR — сформулируй его как аргументированное
сравнение, а не как констатацию.
```

**Действия ведущего:** прочитать план вслух, прокомментировать два-три решения,
при необходимости запросить корректировку. Это точка контроля человеком, дешёвая
по сравнению с правкой готового кода.

#### 4.1b. Сохранить план в репозиторий — обязательный шаг

В plan mode агент **не может писать файлы** — это режим только на чтение.
Поэтому после утверждения плана выходим из режима (Shift+Tab) и первым же
действием сохраняем его:

```
Сохрани утверждённый план в docs/plan.md: целевая архитектура, модель данных,
API обоих сервисов, устройство стенда, порядок работ по этапам, критерий
готовности и сравнение рантаймов с обоснованием выбора.
Это рабочий документ проекта — на него будешь опираться при реализации.
Затем закоммить его отдельным коммитом.
```

**Зачем — проговорить аудитории.** Постройка займёт десятки минут, за это время
контекст сожмётся и детали плана вымоются: агент начнёт достраивать решения
по памяти вместо того, чтобы следовать утверждённым. Файл в репозитории
переживает и сжатие контекста, и перезапуск сессии; его можно вычитать
человеком до старта; в блоке 10 он станет источником для ADR.

**Принцип:** контекст — рабочая память, репозиторий — долговременная.
Всё, что должно пережить сессию, кладём в файл.

### 4.2. Наполнение каталога: парсер и базовый скрипт наполнения

Этап состоит из трёх шагов. Он даёт две демонстрации сразу: работу агента
с незнакомой внешней структурой и срабатывание собственных границ проекта.

#### Шаг 1. Разведка структуры каталога

```
Нам нужен наполненный каталог книг. Источник структуры — публичный каталог
площадки самиздата author.today.

Сначала разведка, без написания парсера: изучи, как устроена страница списка
книг и карточка книги, какие поля доступны (название, автор, серия, жанры,
теги, цена, рейтинг, число прочтений), как устроена пагинация.
Проверь robots.txt источника и скажи, что он разрешает.

Ничего не сохраняй, просто опиши структуру и ограничения.
```

**Затем — зафиксировать результат разведки в файле:**

```
Сохрани результат разведки в docs/research/catalog-source.md: структура
страницы списка и карточки, доступные поля, устройство пагинации,
что разрешает robots.txt, ограничения по частоте запросов.

Сохраняй свои структурированные выводы, а не текст страниц: разметку
и содержимое чужих страниц в репозиторий не копируем.
Этот документ — обоснование для селекторов будущего парсера.
```

**Что проговорить:** сохраняем **дистиллят, а не сырьё**. Это и опрятность
(в репозитории нет чужого контента), и мера против инъекции: разобранные
выводы вместо загруженного текста. Файл переживёт сжатие контекста и объяснит
будущему читателю, почему селекторы парсера именно такие.

> **Ожидаемое поведение (проверено на прогоне).** Агент выходит в сеть
> встроенным инструментом `WebFetch` — в выводе строки вида `Fetch(https://…)`.
> Запрет `Bash(curl:*)` и hook с matcher `Bash` при этом **не срабатывают**,
> и это корректно: запрет `curl` защищает от выполнения чужого кода, а не
> от чтения страницы. Закрывать `WebFetch` не нужно — чтение сети и есть
> задача этого шага. Развёрнутый разбор для эфира — в заметках спикера, блок 5.

#### Шаг 2. Парсер как инструмент проекта

```
Создай парсер каталога как консольную команду проекта в tools/catalog-parser/
с аргументами: источник, лимит страниц, путь вывода.

Структуру источника, поля и пагинацию бери из @docs/research/catalog-source.md —
это результат нашей разведки. Модель данных каталога — из @docs/plan.md,
поля парсера должны ей соответствовать. Если в разведке чего-то не хватает
для реализации — скажи, чего именно, вместо того чтобы догадываться.

Требования — они уже описаны в .claude/rules/scraping.md, следуй им:
- запросы через HTTP-клиент приложения, не через shell;
- уважать robots.txt, не чаще одного запроса в секунду, backoff на 429 и 5xx;
- описательный User-Agent;
- кэш ответов локально, чтобы повторный запуск не ходил в сеть заново;
- на выходе JSON в storage/catalog/, каталог добавлен в .gitignore;
- собирать только структурные метаданные: название, автор, серия, жанры,
  теги, цена, рейтинг. Обложки и полный текст аннотаций не сохранять;
- селекторы разметки — в одном месте и с комментариями: внешняя разметка
  меняется, и правят именно этот файл;
- тесты на сохранённых HTML-фикстурах, не на живых запросах.
```

#### Шаг 2b. Момент, когда становится нужен разработчик

Этот шаг **намеренно не сделан заранее**. К концу работы над парсером основная
сессия заметно заполнена деталями реализации — и потребность в делегировании
становится наблюдаемой, а не декларируемой. Это живая иллюстрация принципа
естественного наращивания: возможность добавляют, когда возникла нужда.

**Сначала показать проблему:**

```
/context
```

Прокомментировать, что занимает окно: системный промпт, CLAUDE.md и правила,
и — растущая история постройки. Дальше будет только больше.

**Затем создать исполнителя:**

```
Постройка идёт долго, и основная сессия заполняется деталями реализации.
Создай субагента implementer в .claude/agents/ — исполнителя одного этапа
плана: код, тесты, коммит.

tools: Read, Grep, Glob, Edit, Write, Bash; model: sonnet.
Источник истины для него — docs/plan.md: он не видит нашу переписку,
поэтому всё нужное берёт из репозитория (план, CLAUDE.md, .claude/rules/).

Границы в инструкции: реализует ровно один названный этап и останавливается;
не трогает .claude/**; не выполняет деструктивных команд и не пушит;
при отказе в правах сообщает, а не ищет обход; если план противоречив —
останавливается и докладывает, а не додумывает.

Отчёт: что сделано, какие файлы изменены, результаты тестов и линтера,
хеш коммита, что осталось, расхождения с планом с обоснованием.
Пиши по-английски.
```

**Ожидаемый результат:** четвёртый субагент, единственный с правом записи.
**Проверка:** `/agents` показывает его; в frontmatter есть `Edit`, `Write`, `Bash`.
**Запасной вариант:** `reference-config/.claude/agents/implementer.md`.

**Что проговорить — это методическая кульминация блока 6:**

1. **Ограничение «только чтение» относилось к ревьюерам, а не к субагентам
   вообще.** Проверяющий не должен уметь исправлять — это разделение ролей.
   Исполнитель обязан уметь писать; безопасность обеспечивается не отсутствием
   инструментов, а границами в инструкции и общими permissions с hooks,
   которые продолжают действовать.
2. **Координация — через файл, а не через разговор.** Субагент не видит нашу
   переписку. Работает это только потому, что план сохранён в репозиторий
   на шаге 4.1b. Без него делегировать было бы нечего.
3. **Цена делегирования — наблюдаемость.** Возвращается сводка, а не ход
   работы: меньше видно и труднее вмешаться. Первым заданием исполнителя
   станет следующий шаг — сидер: парсер мы делали основной сессией на виду,
   сидер сделает субагент, и разницу будет видно на соседних задачах.

#### Шаг 3. Базовый скрипт наполнения, работающий без парсера

Выполняется **исполнителем** — это его первая делегированная задача:

```
Используй субагента implementer для этой задачи:

Создать сидер каталога (Laravel Seeder в database/seeders/) на 300 книг
с синтетическими данными. Модель данных и связи — из docs/plan.md;
распределение жанров, диапазоны цен и структуру серий согласовать
с docs/research/catalog-source.md, чтобы синтетика была правдоподобной.

Состав записи: русскоязычные названия и авторы, циклы и серии, жанры
(фэнтези, попаданцы, ЛитРПГ, детектив, романтика, нон-фикшн), теги,
короткие аннотации, цены от 0 до 500 рублей, часть книг бесплатные,
рейтинг и число прочтений.

Это базовое наполнение репозитория: оно должно работать без парсера, чтобы
проект запускался у любого, кто его склонировал. Если рядом лежит выгрузка
парсера в storage/catalog/, сидер использует её; если нет — генерирует
синтетические данные.
```

**Пока исполнитель работает — обратить внимание аудитории:** вместо ленты
вызовов инструментов, как было с парсером, — ожидание и затем сводка.
Это та самая цена делегирования, теперь видимая вживую.

**Проверка (после сводки):** `php artisan db:seed` наполняет каталог без сети;
в сводке есть хеш коммита и результаты тестов; запуск парсера
с малым лимитом страниц создаёт файл в `storage/catalog/`, и повторный прогон
скрипта наполнения подхватывает его.

**Что проговорить аудитории:**

1. Парсер — инструмент разработчика, он живёт в репозитории. Его **выгрузка** —
   нет: `storage/catalog/` в `.gitignore`. Репозиторий публичный, и чужие
   аннотации с обложками в нём не нужны — это вопрос не только права,
   но и гигиены зависимостей.
2. Скрипт наполнения работает без парсера. Проект должен запускаться у любого, кто его
   склонировал, без доступа к внешнему источнику.
3. Дисциплина запросов — `robots.txt`, ограничение частоты, честный User-Agent,
   кэш — это не формальность, а признак инженерного качества парсера. Мы вынесли
   её в правило, и агент следует ей без напоминаний.

### 4.3. Запуск постройки

**Выполняется после того, как исполнитель вернул сводку по сидеру и результат
проверен.** Технически цель довела бы до критерия и недоделанное, но граница
«до этого момента мы управляли каждым шагом — отсюда агент работает сам» должна
быть чистой: она сама по себе содержание блока, и ручные шаги не должны
накладываться на ходы цели.

**Сначала — убедиться, что программа работ записана в план.** Порядок этапов
и критерий готовности должны быть в `docs/plan.md` (шаг 4.1b). Если план получился
без них, дописать перед запуском:

```
Дополни docs/plan.md двумя разделами, если их там нет.

Порядок работ: каркас обоих сервисов → БД и миграции → парсер и сидер каталога →
бизнес-логика и API → тесты на Pest → Dockerfile на каждый сервис →
docker-compose со стендом → Helm-чарт → GitHub Actions → README.
Осмысленный коммит после каждого завершённого этапа.

Критерий готовности:
1. docker compose up поднимает стенд, все контейнеры в состоянии healthy;
2. каталог отвечает: список книг, карточка книги, поиск и фильтр по жанру;
3. заказы отвечают: добавление в корзину, оформление заказа;
4. php artisan test проходит в обоих сервисах;
5. линтер не выдаёт замечаний;
6. helm lint и helm template выполняются без ошибок;
7. рабочий процесс GitHub Actions валиден.
```

**Затем — одна команда, которая и есть запуск.** Отдельный промпт с задачей
не нужен: `/goal` немедленно начинает ход, а само условие служит директивой.

```
/goal проект собран по docs/plan.md и все семь пунктов критерия готовности
из него выполняются: docker compose up поднимает стенд со здоровыми
контейнерами, оба сервиса отвечают на свои эндпоинты, php artisan test
зелёный в обоих, линтер чист, helm lint и helm template без ошибок,
workflow валиден. Порядок этапов и дисциплина коммитов — по плану.
```

**Почему условие сформулировано именно так:**

- `/goal` задаёт **проверяемое состояние**, а не работу. «Реализуй проект» —
  плохая цель: нечего проверять. Перечень наблюдаемых признаков — хорошая.
- Условие ссылается на файл, но ключевые признаки перечислены и в самой
  формулировке: проверяющий видит их напрямую, без чтения плана.
- Программа работ (порядок этапов, коммиты) живёт в плане, а не в цели.
  Цель отвечает на вопрос «когда закончили», план — «что делаем».

**Как это работает дальше.** После каждого хода условие независимо проверяет
быстрая модель: «выполнено» — цель снимается сама; «нет» — начинается следующий
ход; «недостижимо» — цель отменяется. Контекст между ходами сохраняется.
Явного предела числа ходов нет; есть защита от зацикливания, если агент
несколько ходов подряд отвечает без вызова инструментов. Прекратить вручную:
`/goal clear`.

> **Важно для планирования эфира.** Цель **не меняет режим разрешений**.
> В обычном режиме команда, не попавшая в `allow`, остановит цикл и будет ждать
> вашего подтверждения. Полностью безнадзорной постройка будет только в режиме
> `auto`. На репетиции зафиксировать, что именно спрашивалось, и расширить
> `allow` — тогда в эфире остановок будет меньше.

**Про исполнителя на этом этапе.** Демонстрация делегирования уже состоялась —
сидер сделан субагентом на шаге 3. Дальше на занятии постройку ведёт основная
сессия под `/goal`: аудитория должна видеть агентный цикл, а не индикатор
ожидания. В реальной работе, где зрителей нет, разумно наоборот — делегировать
исполнителю больше этапов:

```
Используй субагента implementer для следующего этапа из docs/plan.md.
Когда вернётся отчёт — проверь результат и переходи к следующему.
```

**Далее постройка выполняется в фоновом режиме.** Ведущий возвращается к прогрессу
между блоками на 30–60 секунд и подтверждает накопившиеся запросы.

**Операционные замечания к фоновой работе:**

- При `defaultMode: "default"` команда, не попавшая в `allow`, останавливает
  постройку запросом подтверждения. Постройка не полностью безнадзорна:
  возвращаясь к прогрессу, подтверждать накопившиеся запросы. На репетиции
  зафиксировать, какие команды запрашивались часто, и расширить `allow` —
  это само по себе учебный материал: список доверенных команд выводится
  из практики, а не угадывается заранее.
- `deny Read(**/.env)` не мешает приложению: `.env` читает Laravel, а не агент.
  Агент создаёт `.env.example` (коммитится) и копирует его в `.env` командой,
  которая запросит подтверждение. Перечитать `.env` агент не сможет — это
  ожидаемое поведение границы, а не ошибка.

**Запасной вариант:** эталонная ветка с результатом полного прогона — переключиться
и продолжить занятие с блока 6.

## Этап 5 · Блок 7. Периодические проверки

> **Не запускать `/loop`, пока активна цель из этапа 4.** Оба механизма
> управляют тем, когда начинается следующий ход, но по разным критериям:
> цель — «предыдущий ход завершился и условие не выполнено», цикл — «прошёл
> интервал». Одновременная работа документацией не описана. В блоке 7 команду
> **показываем и разбираем**, а запускаем либо после завершения постройки
> (в блоке 9 или 11), либо в отдельной сессии.

Разбираемая команда:

```
/loop 10m прогони тесты в обоих сервисах и запусти субагента security-auditor
по изменениям с прошлой проверки; сверься с критерием готовности
из docs/plan.md и отметь, какие пункты уже выполняются;
при обнаружении неисправностей устрани их и выполни коммит
```

**Что проговорить, показывая её:** разница механизмов запуска следующего хода —
`/goal` ждёт завершения предыдущего хода и проверяет условие, `/loop` ждёт
истечения интервала. Отсюда и разные применения: доведение задачи против
дежурного наблюдения. Сверка с критерием внутри цикла даёт наблюдаемый прогресс:
не «агент что-то делает», а «выполнено пять пунктов из семи».

Далее демонстрируется job ревью для GitHub Actions:

```
Создай .github/workflows/claude-review.yml: на каждый pull request агент
проверяет изменения по чеклисту project-review в headless-режиме.
Права токена GitHub минимальные (contents: read, pull-requests: write),
права агента — только чтение (Read, Grep, Glob).
Аутентификация — переменная окружения CLAUDE_CODE_OAUTH_TOKEN из секретов
репозитория (оплата по подписке). ANTHROPIC_API_KEY не задавай вовсе:
при наличии обеих переменных приоритет у API-ключа, и подписка
использована не будет.
Actions фиксируй по мажорному тегу; pull_request_target не использовать.
```

**Проверка:** рабочий процесс валиден, блок `permissions` задан явно,
`ANTHROPIC_API_KEY` в файле отсутствует.

**Если оплата по API** — заменить переменную на `ANTHROPIC_API_KEY`
и убрать `CLAUDE_CODE_OAUTH_TOKEN`. Смешивать нельзя.

**Что проговорить аудитории (частый вопрос):** подписка в CI работает —
через `claude setup-token`, — но прогоны расходуют её лимит и конкурируют
с вашей интерактивной работой. Для регулярного ревью на каждый pull request
предсказуемее отдельный API-ключ с собственным бюджетом; для учебного проекта
подписки достаточно.

## Этап 6 · Блок 9. Ревью и документирование

```
Запусти параллельно трёх субагентов по всему проекту: code-reviewer,
security-auditor и db-reviewer. Каждому передай в задании, что эталон
требований — docs/plan.md: проверять нужно не только качество кода,
но и соответствие реализованного утверждённому плану.

Сведи их отчёты в один документ: находки, сгруппированные по слоям,
с приоритетами. Отдельным разделом — расхождения с планом: что из
запланированного не реализовано и что сделано иначе, чем решили.
```

**Почему это важнее обычного ревью:** субагент не видит вашу переписку, поэтому
без указания на `docs/plan.md` он проверит код «вообще», а не то, договорились ли
мы о нём. Раздел с расхождениями — самая ценная часть отчёта: именно там видно,
куда агент отклонился за десятки минут автономной работы.


## Приложение. Проверенные сведения о стеке (17.08.2026)

Требуется повторная сверка перед проведением: версии изменяются.

**Laravel 13** — текущая стабильная ветка, выпущена в марте 2026, требует PHP 8.3–8.5.
Laravel 12 получает только исправления безопасности. Тестовый фреймворк по умолчанию —
**Pest** (PHPUnit также поддерживается), запуск `php artisan test`.

**Laravel Octane 2.x** (актуальная версия 2.19.0) официально поддерживает **FrankenPHP,
RoadRunner, Swoole и OpenSwoole**; сведений об отказе от Swoole в документации нет.
Установка: `composer require laravel/octane`, далее
`php artisan octane:install --server=frankenphp`. Запуск:
`php artisan octane:start --server=frankenphp --host=0.0.0.0 --port=8000`;
плановая перезагрузка воркеров задаётся параметром `--max-requests` (по умолчанию 500),
после развёртывания выполняется `php artisan octane:reload`.

**Существенное ограничение:** `Octane::concurrently()`, ticks/intervals и cache-драйвер
`octane` работают **только на Swoole и OpenSwoole**. На FrankenPHP и RoadRunner они
недоступны — это ограничение внесено в правило `octane.md`, чтобы агент их не применял.

**FrankenPHP** — PHP, встроенный в сервер на основе Caddy: без межпроцессного
взаимодействия, с автоматическим HTTPS, HTTP/2 и HTTP/3. Актуальная версия 1.12.7;
версии 2.x не существует. Репозиторий переведён в организацию `php` на GitHub,
однако образы по-прежнему публикуются как **`dunglas/frankenphp`** — образа
`php/frankenphp` на Docker Hub нет. Схема тегов:
`dunglas/frankenphp:<версия>-php<версия PHP>-<ОС>`, например `1.12.7-php8.4-trixie`.
Расширения устанавливаются через `install-php-extensions`; для Octane обязателен
`pcntl`. Для запуска от непривилегированного пользователя проще всего использовать
порт не ниже 1024 и задать `SERVER_NAME`, тогда capabilities для портов 80 и 443
не требуются.

**RoadRunner** — сервер на Go с отдельными PHP-процессами-воркерами (модель
shared-nothing, взаимодействие по протоколу goridge), с плагинами HTTP, Jobs, gRPC
и встроенным супервизором. Версионирование календарное, актуальная версия 2025.1.15.
Установка: `composer require spiral/roadrunner-cli spiral/roadrunner-http`, затем
`./vendor/bin/rr get-binary`. Образ — `ghcr.io/roadrunner-server/roadrunner:2025.1.15`;
бинарный файл копируется в собственный PHP-образ инструкцией `COPY --from`.
Octane не формирует полноценный `.rr.yaml`: параметры передаются переопределениями,
RPC-порт по умолчанию равен значению порта минус 1999.

**Различие моделей (материал для ADR):** FrankenPHP представляет собой единый
компонент — полноценный веб-сервер с TLS и раздачей статики, PHP исполняется внутри
процесса сервера. RoadRunner — сервер и пул PHP-воркеров: изоляция воркеров, развитая
плагинная модель, схема ближе к классической установке за обратным прокси.

**PostgreSQL** — драйвер `pgsql`, поддерживаются версии от 10; в контейнере необходим
`pdo_pgsql`. В Laravel 13 добавлены пулированные соединения (для PgBouncer) и нативный
векторный поиск через pgvector; упоминание уместно, применение в учебном проекте
не обязательно.
